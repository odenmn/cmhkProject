# JOINCOM × CMHK 管理后台 V1 改造执行说明书

## 0. 文档用途

本文件是 Codex 改造现有 `cmhkProject` 的唯一执行说明，不是汇报材料。

执行前必须依次读取：

1. `.codex/PROJECT_RULES.md`
2. `.codex/PROJECT_STATUS.md`
3. 本文件
4. 与当前阶段相关的源码和数据库脚本

每次只执行一个阶段。开始编码前先输出本阶段影响文件、数据表和测试范围；发现本文与现有代码或真实数据库不一致时，停止修改并报告冲突，不得自行扩大需求。

## 1. 改造目标与边界

### 1.1 V1 目标

在保留现有 Spring Boot、Vue 管理端、MySQL 和 Redis 技术基础的前提下，把当前后台改造成以 JOINCOM 内部运营为主的 CMHK 业务管理后台，形成以下闭环：

> 渠道 → 客户 → 订单 → UMALL 办理状态 → ICCID/推荐号码资源 → 任务与异常 → 渠道佣金/客户返现 → 基础分析

V1 建设八个业务域：

1. 渠道生态域
2. 客户运营域
3. 订单履约域
4. 资源运营域
5. 产品运营域
6. 任务运营域
7. 收益结算域
8. 数据分析域

### 1.2 V1 使用者

- 主要使用者：JOINCOM 内部管理员、运营人员。
- 数据提供和协作方：CMHK、返现易、合作渠道。
- V1 不开发完整的 CMHK 独立查看端和渠道门户，但账号、角色和数据范围设计不得阻碍后续扩展。

### 1.3 明确不做

- 不替代 UMALL 的正式办理、审核、上台、激活和合约管理。
- 不在本系统上传或存储身份证件、地址证明、通行证、护照等正式身份文件。
- 不拆分微服务，继续使用 Spring Boot 模块化单体。
- 不开发高级 BI、大屏、完整活动中心、AI 客服或自动打款。
- 不因为业务域命名而一次性移动所有现有类；以可运行、可迁移为第一原则。
- `frontend/` 移动端 H5 暂停扩展，只做与后台数据模型变化相关的兼容修改。

## 2. 当前代码基线

### 2.1 可直接复用

- `backend/`：Spring Boot 3、Java 21、MyBatis Plus、统一响应、异常处理、Redis 缓存。
- `admin-frontend/`：Vue 3、TypeScript、Element Plus、管理端布局和路由。
- 客户、订单、套餐基础数据结构。
- ICCID 库存、分配、解绑、使用和历史记录。
- CMHK 文件预览、SHA-256 防重、确认导入、自动匹配和异常匹配。
- 二级渠道佣金规则、规则快照、BigDecimal 计算、人工调整和确认。
- 管理员登录、操作日志和首页基础指标。

### 2.2 已确认的结构问题

| 编号 | 问题 | 改造要求 |
|---|---|---|
| B-01 | `channel` 与 `secondary_channel` 是两套渠道主档 | 统一为 `channel` 主档，旧表过渡期只读 |
| B-02 | 管理员令牌只接受 `ADMIN` | 增加角色和数据范围，不再硬编码单角色 |
| B-03 | 订单状态分散且管理端允许自由文本输入 | 建立统一状态字典、状态转换和历史记录 |
| B-04 | 只有对账异常，没有统一运营任务 | 新建任务中心并由业务事件生成任务 |
| B-05 | 资源域只有 ICCID | 增加推荐号码接龙池及分配历史 |
| B-06 | 只有渠道佣金，没有客户返现 | 增加返现计划和返现易结果导入 |
| B-07 | 套餐只有查询能力，缺少管理端维护 | 增加套餐、权益、渠道适用范围管理 |
| B-08 | H5 仍采集并保存 `id_no` | 停止采集和写入；历史清理需单独确认 |
| B-09 | `schema.sql` 同时承担初始化和持续升级 | 新增增量迁移目录，禁止直接依赖覆盖式建表升级真实库 |

真实数据库结构可能包含 `customer-backup-import.sql` 中的增量字段。每个涉及数据库的阶段开始前，必须先导出 `SHOW CREATE TABLE` 结果并与脚本核对。

## 3. 目标模块与现有代码映射

| 目标业务域 | 现有代码 | 改造方式 |
|---|---|---|
| 渠道生态 | `module/channel`、`AdminSecondary*` | 统一渠道主档，保留入口和结算关系 |
| 客户运营 | `module/customer`、`AdminCustomer*` | 保留客户主档，增加负责人、跟进记录和规范状态 |
| 订单履约 | `module/mobile`、`AdminOrder*`、`Reconciliation*` | 保留订单主表，增加规范状态、状态历史和UMALL原始状态 |
| 资源运营 | `AdminIccid*`、`Iccid*` | 保留ICCID，新增推荐号码池 |
| 产品运营 | `MobilePlan*`、`MobilePlanOffer*` | 增加管理端CRUD和渠道产品政策 |
| 任务运营 | 对账异常页面 | 新建统一任务表、服务和管理页面 |
| 收益结算 | `SecondarySettlement*` | 佣金保留并关联统一渠道；新增客户返现 |
| 数据分析 | `AdminDashboardService*` | 增加渠道、办理、异常、收益基础指标 |

`module/admin` 当前可继续作为管理端接口层。新增核心业务逻辑优先放入对应业务模块，管理端 Controller 只调用业务 Service，不在 Controller 中堆积规则。

## 4. 核心数据设计约束

### 4.1 渠道统一

以现有 `channel` 为唯一渠道主档，增量增加：

- `channel_type`：`RESOURCE`、`ORGANIZATION`、`ENTERPRISE`、`SALES_AGENT`
- `parent_channel_id`：渠道层级，可空
- `contact_name`、`contact_phone`
- `cooperation_status`：`PENDING`、`ACTIVE`、`SUSPENDED`、`ENDED`
- `settlement_info`
- `owner_user_id`：JOINCOM内部负责人，可空

新增 `channel_legacy_mapping` 保存 `secondary_channel.id → channel.id` 的迁移映射。迁移 `secondary_commission_record.channel_id` 后，`secondary_channel` 进入只读兼容期；至少完成一次完整验收和一次备份后，才允许另行决定是否删除。

客户归属继续通过 `customer.channel_id` 和 `customer_channel_binding` 表达。二者出现冲突时，以绑定表为业务事实，并同步修正客户主表冗余字段。

### 4.2 用户、角色与数据范围

扩展 `admin_user`：

- `role_code`：V1启用 `ADMIN`、`OPERATOR`
- `scope_type`：`ALL`、`CMHK`、`CHANNEL`
- `scope_id`：当范围为具体合作方时保存对应ID

预留 `CMHK_VIEWER`、`CHANNEL_VIEWER`，V1不开放对应门户。

后端令牌验证结果必须返回包含用户ID、账号、角色和数据范围的 Principal；Controller 和 Service 不得只依赖用户名。权限至少区分：

- 系统配置和用户管理：仅 `ADMIN`
- 日常客户、订单、资源、任务：`ADMIN`、`OPERATOR`
- 佣金规则修改、结算确认、返现确认：仅 `ADMIN`

### 4.3 订单状态

保留 `mobile_plan_order` 作为 V1 订单主表，不进行无收益的改名。

规范字段：

- `status`：JOINCOM统一办理状态
- `review_status`：UMALL审核状态
- `supplement_status`：补件状态
- `activation_status`：激活状态
- `contract_status`：合约状态
- `umall_status`：UMALL原始状态文本，不参与系统规则判断
- `status_updated_at`

统一办理状态只允许：

- `PENDING`
- `FOLLOWING`
- `SUBMITTED_UMALL`
- `UNDER_REVIEW`
- `NEED_SUPPLEMENT`
- `WAITING_ACTIVATION`
- `ACTIVATED`
- `COMPLETED`
- `AFTER_SALES`
- `CANCELLED`

新增 `order_status_history`，记录订单、状态类型、变更前、变更后、来源、操作人、变更时间。管理端不得继续用自由文本编辑关键状态。

CMHK导入时：原始值先保存到对账行，再通过集中映射器转换为标准状态；无法识别的状态不得覆盖订单，必须生成异常任务。

### 4.4 任务中心

新增 `operation_task`：

- 任务类型：`CUSTOMER_FOLLOW_UP`、`SUPPLEMENT`、`REVIEW_EXCEPTION`、`ACTIVATION_EXCEPTION`、`RESOURCE_SHORTAGE`、`CASHBACK_EXCEPTION`、`AFTER_SALES`
- 关联：客户、订单、渠道和来源记录ID均可空
- 状态：`PENDING`、`PROCESSING`、`DONE`、`CLOSED`
- 字段：负责人、优先级、截止时间、处理结果、创建来源、完成时间

相同业务对象、相同任务类型只允许一个未完成任务。任务完成只代表人工动作完成，不得直接伪造UMALL、返现易等外部事实状态。

### 4.5 推荐号码接龙池

新增：

- `referral_number_pool`
- `referral_number_assignment_history`

号码来源必须关联已成功上台的订单或经过人工确认的导入记录。分配时按可用顺序取一个号码，并使用数据库事务和行锁避免重复分配。状态至少包括 `AVAILABLE`、`RESERVED`、`USED`、`DISABLED`。

推荐号码只服务需要接龙的学生类办理，不得对所有订单强制分配。

### 4.6 收益结算

现有渠道佣金规则和快照继续使用，但渠道ID迁移为统一 `channel.id`。

新增客户返现：

- `customer_cashback_plan`：订单、规则快照、计划总额、期数、状态
- `customer_cashback_installment`：计划期次、计划金额、计划日期、返现易状态、到账时间、提现状态、异常原因
- `cashback_import_batch`、`cashback_import_row`：返现易文件预览、确认和异常匹配

返现易是到账和提现事实来源；JOINCOM只管理规则、计划、匹配、展示和异常任务。实际付款或结算必须人工确认。

### 4.7 产品与渠道政策

保留 `mobile_plan`、`mobile_plan_offer`，新增 `channel_product_policy`：

- 渠道ID
- 套餐ID
- 是否可推广
- 生效和失效日期
- 返现规则引用
- 佣金规则引用

订单继续保存套餐快照，修改套餐不得回写历史订单。

### 4.8 隐私边界

第一阶段停止 H5 采集和后端写入 `id_no`。旧字段暂时保留为空以兼容历史代码；是否清空真实数据库中的历史证件号码属于不可逆数据操作，Codex必须先输出影响数量并取得用户明确确认。

## 5. 分阶段执行计划

### 阶段 P0：改造安全基线

目标：在修改业务结构前建立可迁移、可回滚的基础。

任务：

1. 新增 `backend/src/main/resources/db/migrations/`，所有真实库升级使用按序编号的增量SQL。
2. `schema.sql`只维护全新安装的最终结构，不把它当作真实库升级脚本直接执行。
3. 记录升级前表结构、数据量和关键唯一性检查SQL。
4. 从 H5、请求DTO、Service 写入逻辑移除 `idNo`；响应中不返回该字段。
5. 不自动清空历史 `id_no` 数据。
6. 为后续改造建立后端测试基线和两个前端类型检查基线。

验收：

- 新订单不再写入证件号码。
- 现有客户、订单、ICCID、对账和佣金功能不受影响。
- 后端测试通过，两个前端 TypeScript 检查通过。

### 阶段 P1：统一渠道与权限

依赖：P0。

任务：

1. 扩展 `channel` 字段，新增渠道迁移映射表。
2. 将 `secondary_channel` 数据合并到 `channel`，编码冲突必须进入迁移异常清单。
3. 更新佣金记录指向统一渠道ID。
4. 后端渠道查询、客户渠道下拉框、渠道档案页面统一使用 `channel`。
5. 旧 `secondary_channel` 写接口停用，保留只读兼容。
6. 扩展管理员角色、Principal和接口权限。
7. V1暂不建设渠道登录端和CMHK登录端。

验收：

- 一个渠道只有一个主档ID。
- 客户归属、渠道订单和佣金记录均能追溯同一渠道。
- 运营人员无法修改管理员、佣金规则或确认结算。
- 迁移前后渠道数、客户绑定数、佣金记录数有核对报告。

### 阶段 P2：客户、订单与产品标准化

依赖：P1。

任务：

1. 增加客户负责人和客户跟进记录。
2. 建立标准订单状态和 `order_status_history`。
3. 将管理端订单状态输入框改为受控选项和允许的状态动作。
4. 将UMALL原始状态与JOINCOM标准状态分开保存。
5. 完善CMHK文件导入状态映射，未知状态生成异常而非覆盖。
6. 增加套餐、权益和渠道产品政策管理页面及接口。

验收：

- 任一订单可以查看完整状态变更历史。
- 文件重复导入保持幂等。
- 未知或冲突状态不会覆盖订单。
- 历史订单套餐金额和规则快照不随产品修改变化。

### 阶段 P3：资源运营补齐

依赖：P2。

任务：

1. 保留现有ICCID功能并统一资源模块接口风格。
2. 新增推荐号码池、导入、查询、保留、分配、使用、停用和历史记录。
3. 学生类订单支持分配推荐号码，其他订单不展示该动作。
4. 增加库存不足和接龙中断检测入口。

验收：

- 并发分配不会让两个订单占用同一ICCID或推荐号码。
- 分配、解绑、使用均有操作日志和资源历史。
- 资源可从订单和客户详情双向追溯。

### 阶段 P4：任务与异常闭环

依赖：P2；资源异常部分依赖P3。

任务：

1. 新建任务表、Service、管理端列表和详情。
2. CMHK导入产生补件、审核异常和激活异常任务。
3. ICCID不足、推荐号码中断产生资源任务。
4. 客户详情和订单详情展示关联任务。
5. 支持领取、转派、处理和关闭，记录处理历史。

验收：

- 相同来源不会重复创建未完成任务。
- 任务处理不会越权改变外部事实状态。
- 首页能够统计各类待处理任务。

### 阶段 P5：收益结算完整化

依赖：P1、P2、P4。

任务：

1. 完成渠道佣金与统一渠道ID适配。
2. 新增客户返现计划、期次和状态。
3. 新增返现易文件预览、确认、匹配和异常处理。
4. 返现异常自动生成任务。
5. 客户和订单详情同时展示渠道佣金与客户返现，但按权限隐藏敏感金额。

验收：

- 渠道佣金和客户返现是两个独立业务对象。
- 规则修改不影响历史快照。
- 返现易到账和提现状态可追溯至原始导入批次。
- 未经管理员确认不得将结算标记为已完成。

### 阶段 P6：基础数据分析

依赖：P2至P5。

任务：

1. 增加按渠道统计客户量、订单量、上台量、激活量和转化率。
2. 增加稽核补件、任务积压、资源库存、佣金和返现基础指标。
3. 支持时间范围和渠道筛选。
4. 不建设复杂大屏和预测模型。

验收：

- 指标能够回溯到明细数据。
- 指标口径在代码常量或说明中集中定义。
- 渠道筛选遵守用户数据范围。

## 6. API与前端执行规则

### 6.1 API

- 管理端接口继续使用 `/api/admin/**`。
- 新增接口按业务域分组，例如 `/api/admin/tasks`、`/api/admin/referral-numbers`、`/api/admin/cashbacks`。
- 所有列表接口必须支持服务端筛选；数据量扩大后不得依赖前端全量过滤。
- 创建、状态变更、分配、导入确认和结算确认必须记录操作日志。
- 金额继续使用 `DECIMAL` 和 `BigDecimal`。

### 6.2 管理端

建议最终菜单：

1. 业务首页
2. 渠道管理
3. 客户管理
4. 订单履约
5. 产品管理
6. 资源管理（ICCID、推荐号码）
7. 任务中心
8. 收益结算（渠道佣金、客户返现）
9. 数据导入（CMHK、返现易）
10. 系统管理（用户、日志）

原页面优先调整和复用，不为了菜单重组重新制作全部UI。
